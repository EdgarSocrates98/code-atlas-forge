# Review — lf-0029 (Cycle 3.1 Phase 3 — LSP runtime hardening)

## Veredito

**ACCEPTED** — lifecycle auditado, 3 gaps reais implementados e
provados com fixture; segurança re-verificada; doc honesta sobre
real vs fixture.

## Auditoria → gaps fechados

Já coberto: handshake/capabilities, definition/references,
`$/cancelRequest` após timeout, shutdown→exit ordenado, crash →
`available=False`, `MAX_LSP_SERVERS=4`, env whitelist, argv sem
shell, transporte POSIX/Windows. Implementado nesta spec:

- `documentSymbol` — `LspClient.document_symbol()` capability-gated.
- `publishDiagnostics` — notificação capturada por uri no loop de
  request e anexada ao resultado como `server-diagnostic` (info).
- Recovery pós-falha — `LspClient.restart()` (close+start);
  adapter: 1 restart + 1 retry em timeout/LspError/TransportError;
  falhando → `server-error`/`request-timeout` tipado. Nunca crash.

## Decisões registradas

- Timeout também dispara recovery — server wedged é
  indistinguível de crash na borda do transporte.
- `documentSymbol` fica no client, não no adapter — o resolver só
  consome definition/references por `kind` (documentSymbol é
  capacidade de inventory futura, lf-0030+).

## Riscos restantes

- Sem server real no CI: fixtures de protocolo cobrem framing/
  lifecycle, não semântica de um pyright real. E2E real fica
  disponível para qualquer operador que instale um server.
