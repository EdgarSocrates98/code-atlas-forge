## O que foi entregue

- **Schema v4** (`migrations.py`): `parse_result_cache` — chave de
  validade completa `UNIQUE(repo, path, sha, lang, parser_v, grammar_v,
  extractor_v, resolver_v, builder_v, config_digest)`. Migração com
  checksum como v1–v3; `docs/database-schema.md` atualizado.
- **`indexing/cache.py`**: codec `ParseResult`↔JSON estruturado (sem
  pickle/marshal — verificado por auditoria estática). `payload_sha256`
  na leitura → blob corrompido/formato inválido = miss, nunca crash.
  `get` é leitura pura (WAL-friendly); `hit_count`/`last_used` escritos
  só na transação de publicação via `mark_used`.
- **`indexing/reuse.py`** (reescrito): `config_digest` (adaptadores +
  limites do engine) e `cache_key_for` — monta a CacheKey do
  SourceFile+adapter.
- **Coordinator**: REUSE → cache hit devolve `ParseResult` sem ler o
  arquivo nem chamar tree-sitter; miss → leitura+parse reais.
  REVALIDATE/REPARSE sempre re-parseiam (decisão conservadora: spec
  exige "reuse only when dependency set unchanged; otherwise
  reevaluate" — reevaluate = re-extração + re-resolução). Grafo é
  montado com resultados de TODOS os arquivos e persistido inteiro —
  linhas **novas** por snapshot (isolamento lógico). `cache.put` +
  `mark_used` + `gc` dentro da transação de publicação → rollback não
  deixa órfãos.
- **Substituiu o copy-forward do lf-0019** (`copy_*`,
  `reconstruct_universe`, `preserved_universe`, `external_occ` removidos
  — dead code). O cache é o mecanismo de reuse; o grafo completo
  reconstrói contextos de resolução de verdade, eliminando a
  aproximação anterior.
- **GC**: retenção `KEEP_SNAPSHOTS=5` últimos READY + cap
  `MAX_ENTRIES=50_000` por repo (LRU por `last_used_snapshot_id`).
  Nunca toca linhas de snapshot (cache rows não pertencem a snapshots).

## Achados durante a implementação (bugs reais corrigidos)

1. **fd double-close cross-thread** (`scanner.py`): após
   `os.fdopen(fd)` assumir posse, o `finally: os.close(fd)` fechava
   novamente — sob threads, o número do fd podia ser reutilizado por
   outro worker entre o close do `with` e o close do `finally` →
   `EBADF` no read do outro → `sha256=None` intermitente → **manifests
   divergentes entre dois indexers → dois READY** (o teste de
   concorrência flagrava ~15% das runs). Fix: `fd=-1` após posse
   transferida. Repro: 4-6/40 falhas → **0/60** pós-fix.
2. **`importlib.metadata.version` não thread-safe** no primeiro acesso
   concorrente (crash `OSError` lendo METADATA) → `_pkg_version`
   memoizado com lock (`tree_sitter_runtime.py`).
3. **`O_NONBLOCK` residual** em fd de arquivo regular: limpo via
   `os.set_blocking(fd, True)` após `fstat` confirmar regular
   (hardening; o flag só serve na janela open→fstat p/ FIFO).
4. **`cache.get` escrevia `hit_count`** fora de transação → implicit
   txn → "cannot start a transaction within a transaction". `get`
   agora é read-only; o bump migrou para `mark_used`.

## Riscos restantes

- REVALIDATE re-parseia (conservador) — futuro: permitir cache-hit
  para REVALIDATE se a política for relaxada (basta mover para
  `cache_paths`).
- `repositories.root_handle` continua sem UNIQUE constraint — o
  `INSERT ... WHERE NOT EXISTS` é atômico o bastante sob o lock de
  escrita serializado, mas um índice UNIQUE seria a garantia formal.
- Cache payload é JSON por arquivo — entradas grandes de arquivo
  grande ocupam proporcionalmente (cap 50k/repo mitiga).
