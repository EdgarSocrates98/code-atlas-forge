`semantic-status` lê só o snapshot READY persistido; distinção
honesta installed/enabled/used sem inventar cobertura.

## Evidência

- `index --scip PATH`: sobrescreve `[resolvers.scip].index_path` na
  invocação (proveniência lf-0028 intacta — `versions_out["resolver:
  scip"]` continua na identidade do índice).
- `index --resolver NAME` (repetível/vírgula): filtra a tabela
  efetiva — `syntactic` sempre baseline; `scip`; `lsp`; `lsp:<nome>`.
  Nome desconhecido → erro tipado `--resolver: resolver desconhecido
  'x'` + exit 1 (verificado verbatim — nunca flag silenciosa).
- `semantic-status --json`: `describe_resolvers` (bootstrap) —
  `installed` = artefato presente (SCIP carrega; `shutil.which` para
  binário LSP — nenhum server spawnado); `enabled` = produziria
  resolver (assessment não-rejected / spec.enabled); `used` =
  `relations.resolver` GROUP BY — única fonte autoritativa.
- Cobertura: `GROUP BY resolver, resolution_status` no READY;
  arestas sintáticas com parser-id (`tree-sitter-python`) agregadas
  ao tier baseline (fix do double-count).
- `revision`: `commit_sha` + `analyzer_versions["resolver:scip"]`
  (sha16 do índice que produziu o snapshot).
- `semantic`: counts do último `index_jobs` (attempted/enriched/
  diagnostics).
- Sem migration — os dados já estavam persistidos (relations.resolver,
  analyzer_versions, job counts).
